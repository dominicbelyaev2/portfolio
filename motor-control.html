Closed-Loop DC Motor Control

Role: sole author — firmware, control design, tuning, and Python client · Tools: C (Pico SDK 2.2.0), Raspberry Pi Pico 2 (RP2350), PIO, DRV8833 H-bridge, INA219 current sensor, quadrature encoder, Python + matplotlib · Timeline: Jan – Mar 2026 (ME 333, Intro to Mechatronics)

Bench setup · System layout sketch

Built a cascaded motion controller for a brushed DC motor from scratch in C: a 1 kHz PI current loop nested inside a 200 Hz PID position loop, driven over an 18-command serial interface. Tracked smooth cubic trajectories to a mean absolute error of 5.56° over a ±90° sweep and 8.06° over ±180°, with the inner loop holding a ±100 mA square-wave current reference to 12.3 mA mean error.

Problem

Drive a brushed DC motor to arbitrary angular trajectories with no off-the-shelf motion controller — only a microcontroller, an H-bridge, a current sensor, and an encoder. Torque in a brushed motor is proportional to current, so position cannot be controlled well by commanding duty cycle directly: the controller has to close a fast loop on current first, then wrap a slower loop around position that asks the current loop for the torque it needs.

Architecture

  • Inner loop — current (PI), 1 kHz in a repeating-timer ISR. Reads the INA219 over I²C, computes error against the commanded current, and writes a signed duty cycle to the H-bridge.
  • Outer loop — position (PID), 200 Hz in a second ISR. Reads the encoder, and its output is the current setpoint handed to the inner loop — the two loops are genuinely cascaded, not independent.
  • Motor drive: DRV8833 H-bridge, sign-magnitude PWM on both inputs so a single signed −100…+100 command covers both directions.
  • Feedback: quadrature encoder decoded on the RP2350's PIO blocks, so counting never competes with the control ISRs for CPU time. 1336 counts/rev → 0.27° resolution.
  • Firmware structure: a five-state machine (IDLE, PWM, ITEST, HOLD, TRACK) that both ISRs switch on, so the same timers serve open-loop testing, current-loop testing, and trajectory tracking.
  • Host link: Python client over USB serial — sets and reads gains, runs tests, uploads trajectories, and pulls logged arrays back for plotting.
  • Power: 6 V battery pack for the motor rail, 3.3 V from the Pico for the sensors.

Firmware features

  • Encoder read in raw counts or degrees, with zeroing
  • Current read in mA, calibrated through the INA219
  • Open-loop PWM duty command for bring-up
  • Set / get gains independently for both loops
  • ITEST: automated ±100 mA square-wave current-loop test
  • Step and cubic reference trajectories uploaded from the host
  • On-board logging of reference vs. actual, replayed to the host after each run
  • Motor de-energize and mode query for safe stops

Python client interface — 18 single-key commands over USB serial

Tuning and results

Gains were tuned by hand, loop by loop: the current loop first against the square-wave ITEST until it tracked crisply, then the position loop on top of it. The oscillating run in the first clip above is what the position loop does at Kp 100 with no derivative term; everything below is after tuning. The figure quoted on each plot is the mean absolute tracking error the Python client computed over that run — the mean of |reference − measured| across every sample.

Reference trajectories are regenerated exactly from the trajectory generator; measured traces are recovered from the original run captures and re-plotted on labelled time axes. On the current-loop plot the shaded band is the true sample-to-sample spread, not a smoothed line.

Current loop. 400 samples at 1 kHz. Tracking is noticeably noisier on the negative half of the square wave than the positive — a real asymmetry in the drive/sense path I never chased down.

Step reference. 0→90°→0 over 4 s. Overshoots to ~127° (about 41%) and undershoots on the way back down — the clearest evidence of the missing anti-windup.

Cubic, ±90°. 6 s, 1200 samples. Error is almost entirely lag on the steep segments — the measured trace is the right shape, just slightly behind.

Cubic, ±180°. Same gains, double the sweep. Error grows by roughly the same factor as the demanded rate, which is what a lag-dominated error should do.

Why the step number is worse: a step reference demands an instantaneous jump the motor physically cannot make, so the error metric is dominated by rise time rather than by controller quality. It's a useful stress test of overshoot and settling, but the cubic runs are the fair measure of tracking performance — which is why the same controller reads 15° on one and 5.6° on the other.

What I’d change

  • Add anti-windup. The integrator keeps accumulating while the duty-cycle command is saturated at ±100, so a long saturated move winds up error the loop then has to unwind. Conditional integration — or back-calculation from the clamped output — would kill most of the step overshoot.
  • Fix the derivative term. It's a raw sample-to-sample error difference with no division by the timestep and no filtering, which makes Kd unit-dependent on the loop rate and sensitive to encoder noise. A filtered derivative on measurement rather than error would be better behaved.
  • Log to file, not to a live plot window. Data was plotted straight from the serial stream, so the runs above can't be re-analyzed. Writing timestamped CSV would let me report settling time and steady-state error properly instead of a single mean-error figure.
  • Report better metrics. Mean absolute error flatters smooth references and punishes steps. Overshoot, 2% settling time, and steady-state error describe the controller far more honestly.

What I took away

This was my first time writing a control loop that runs against real hardware instead of a simulation, and the gap between the two is the lesson. The cascade only works because the inner loop is fast enough that the outer loop can treat commanded current as if it were achieved torque — a separation that's obvious on paper and easy to break in practice by mis-setting one timer. Most of the debugging time went to that boundary rather than to the gains.
